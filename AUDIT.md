## 1. Stack identification

| Aspect | Finding |
|---|---|
| Framework | **Hybrid static-first site — no CMS, no SSG, no build step on this machine.** The repo IS the deployable artifact (`dist/`) |
| SPA part | React/Vite single-page app serving exactly two routes: `/` and `/privacy`. Bundle: `dist/assets/index-C6-wz3bb.js` (pre-built; **the Vite source project is not on this machine** — the bundle is binary-patched directly when needed) |
| Static part | ~103 prerendered pages as `folder/index.html` (collections, kits, landing pages, 65 blog posts). Each page's `<head>` is **hand-authored HTML in that file** — there is no template engine and no frontmatter; YAML-style `canonical:` fields do not exist in this stack |
| Source of truth for `<head>` | **Per-page**: each `dist/<page>/index.html` owns its own head. Homepage head = `dist/index.html` (also carries the sitewide Organization/LocalBusiness/FAQ schema). There is no shared partial — this is the root cause of the canonical drift found in §6 |
| Templating | None at runtime. New pages are generated by Python scripts in the session scratchpad (`fab_article_template.py` lineage) and committed as static HTML |

**Implication for later phases:** "refactor into a shared canonical function/partial" cannot be done as a runtime template change. The equivalent is (a) a **lint/fix script** run over `dist/**/index.html` (idempotent, CI-runnable), and (b) fixing the page-generator scripts.

## 2. Routing & URL model

| Aspect | Finding |
|---|---|
| Router | Apache (`php:8.3-apache` Docker image), rules in `dist/.htaccess` — **mod_rewrite only**. mod_alias (`Redirect`/`RedirectMatch`) is deliberately banned (dead code in `.htaccess` context here; documented in the file header) |
| Canonical URL convention | **No trailing slash, no `index.html` suffix** (root `/` excepted). Already enforced server-side |
| Trailing-slash handling **[DONE]** | `.htaccess` §8: every `/page/` → 301 → `/page` (root and `/api/` exempt). Verified in the 311-check test suite |
| `/home` duplicate **[DONE]** | `.htaccess` §2: `/home` and `/home/` → 301 → `https://fabrioza.com/` |
| Where a 301 lives | `dist/.htaccess`, single ordered `RewriteRule` chain (redirects before routing). This is the only redirect layer; the fronting nginx (`scalaro-nginx-1` on the VPS) only terminates SSL and proxies |
| HTTPS/www | www→apex and http→https 301s present, `X-Forwarded-Proto`-aware (proxy-safe), localhost-exempt for testing |
| 404 behaviour | No SPA catch-all (removed 2026-07-09 — was causing soft-404s). Unknown routes serve branded `404.html` with real 404 status |

## 5. Current schema audit

**Authoritative schema is static, in each page's `<head>`** (JSON-LD blocks):

- `dist/index.html`: Organization (with `sameAs`: FB/IG/LinkedIn/TikTok), LocalBusiness ×2 (Sialkot factory + McDonough GA office), FAQPage, 5 Product blocks with full AggregateOffer.
- Collection/kit/catalog pages: ItemList + per-product `Product` with `offers` (AggregateOffer: `lowPrice/highPrice/priceCurrency/offerCount/availability/priceValidUntil`), `image`, `description`, `brand`. **This stack passed GSC validation July 2026** (offerCount ×16 PASSED, availability ×8 PASSED; 172 valid items).
- Priceless category lists (e.g. `/sportswear-catalog`): plain `ListItem`s, intentionally NOT Product (this was the fix for the last 16 GSC criticals).
- Blog posts: Article/BlogPosting + BreadcrumbList on most; **author is the organization, not a named Person** → E-E-A-T gap, in scope for Phase 4.
- Guides/country pages: Service + FAQPage.

**Misconfigured `SearchAction` — [PARTIAL, defused but present].** The React bundle contains
`potentialAction:{"@type":"SearchAction",target:"https://fabrioza.com/?s={search_term_string}",…}`
inside its runtime JSON-LD injector. That injector was **disabled 2026-07-10** (script type renamed to `application/ld+json-disabled`, confirmed: the bundle contains only the disabled type string), so **no parser receives the `{search_term_string}` artifact today** — 0 hits in any static HTML. Phase 1 action: strip the SearchAction from the bundle string outright (site has no search, so per this brief's own rule it should be **removed, not fixed**) + re-apply on future bundle merges.

**Standing constraint:** never add `review`/`aggregateRating` (no real review data; fake ratings = spam-policy risk). The two yellow GSC warnings (172 items each) are intentionally permanent.

## 16 Oct 2026 - form attachments: the file input was never wired

**The fault.** The contact form has carried a file input accepting
`.jpg,.jpeg,.png,.pdf,.ai,.eps` since launch. It had **no `name`, no
`onChange`, no `ref` and no `value`** - React never read it - and the form
posts `application/json`, which cannot carry a file. Customers attached tech
packs and artwork, saw "Thank you", and the file was never read by JavaScript,
let alone uploaded.

Nothing was lost, because nothing was ever sent. There is no backlog to
recover: no files exist on the server, in the database, or in any email.

**The fix.** The submit handler already built a `FormData` from the form
element, so the input only needed a `name` - no state plumbing. Files are then
base64-encoded into the existing JSON envelope rather than switching the
endpoint to multipart, which would have meant rewriting the CSRF and JSON
parsing that currently work.

- `dist/api/uploads.php` (new) - validation and storage
- `lead_files` table in `db.php`
- `send-email.php` stores attachments and names them in the notification
- `dist/admin/file.php` (new) - authenticated download, streamed
- `lead.php` - Attachments card, and files are erased on GDPR delete
- Dockerfile - `post_max_size = 24M` (base64 is 4/3 of raw, so a 10 MB file is
  ~13.4 MB on the wire; PHP's default 8M would have rejected it with an empty
  `$_POST` and no useful error)

**Decisions worth keeping:**

- **Type is decided by MAGIC BYTES, never the filename.** A `.pdf` containing
  HTML is rejected; a real PDF named `shell.php` is stored as `.pdf` and
  downloads as `.pdf`.
- **Files go to `/var/data/uploads`, never the web root.** The Dockerfile does
  `COPY dist/ /var/www/html/`, so anything under the web root is destroyed on
  the next rebuild. Nothing in `/var/data` is web-served, so `admin/file.php`
  behind a login is the only route to a file.
- **A rejected attachment never fails the lead.** The enquiry is worth more
  than the file. Rejections are reported in the notification email.
- **The attachment loop has its own try/catch.** It sits inside the lead
  insert's try, whose catch calls `crm_failed_lead_dump()` - so without this, a
  throw while storing a file would suppress the Telegram alert and record a
  lead that IS saved as a failure.

**Tested end to end against the real PHP** (built-in server, throwaway data
dir), not just linted:

| case | lead | file | correct |
|---|---|---|---|
| real PDF + PNG | saved | both stored, magic bytes intact | yes |

| 11 MB | saved | rejected | yes |

| `shell.php` (real PDF) | - | stored and served as `.pdf` | yes |

## 17 Oct 2026 - lead_files never reached production (migration, not schema)

Yesterday's attachment commit put `CREATE TABLE lead_files` inside the
`if ($version < 1)` block in `db.php`. That block is the INITIAL schema: it
runs once, when the database file is created. Production's database was
already at `PRAGMA user_version = 3`, so the block was skipped and the table
was never created. Every lead page fataled:

    PDOException: no such table: lead_files in admin/lead.php:83

**Why the tests passed anyway.** Every local test built a throwaway database
from nothing, so `user_version` was 0 and the initial block always ran. The one
state that mattered - an existing database being upgraded - was never
exercised. A migration is only proved by running it against the OLD shape.

Fixed by moving the table into a numbered step, `if ($version < 4)`, which runs
on every database regardless of age, plus the missing `$version = 3;` so the
chain falls through correctly.

Verified in three separate processes (a new process each time, so the static
`$pdo` cache cannot hide the result):

| case | before | after |
|---|---|---|
| fresh database | - | user_version 4, table EXISTS |
| database rewound to v3 with a lead in it (production's exact state) | v3, table MISSING | v4, table EXISTS, lead preserved |
| opened a third time | v4 | v4, no error - migration is idempotent |

The `lead.php` query that was fataling now runs.

**Rule for this project: a new table or column goes in a NEW numbered
migration, never into the v1 block.** Test it against a database at the old
version, not a fresh one.

the cPanel mail host has firewall-banned the server's IP on every port

been retrying 3x per email with a dead password for weeks, which is exactly
what trips it. September's failure was "Could not authenticate"; this one is
"Could not connect" - a different fault with the same root cause.

**What was added.** `resendSend()` (HTTPS POST to api.resend.com, port 443,
cURL confirmed present in the image) and `fab_send()`, one entry point that
tries Resend when `RESEND_API_KEY` is set and falls back to SMTP otherwise.

admin Resend button (which passes `retrySmtp=false` so an admin is not left
watching a 30-second hang).

`if (fab_resend_enabled() || $SMTP_PASS !== '')` - otherwise a box configured
with only Resend would silently skip mail entirely.

**The From address does not change.** Mail still goes out as
`info@fabrioza.com`; Resend is the pipe, not the identity.

**The constraint that will bite if ignored:** DMARC here is
`adkim=s; aspf=s` - strict. Resend must verify the **ROOT** domain
`fabrioza.com`, never a `send.` subdomain, or DKIM signs as
`d=send.fabrioza.com`, fails alignment against an `@fabrioza.com` From, and
every message quietly lands in spam. `p=none` means nothing bounces, so there
would be no error to notice. Written up in `RESEND-SETUP.md`.

and behaviour identical to before (safe to deploy before an account exists);
bogus key -> `resend HTTP 401: API key is invalid`; on failure `fab_send()`
falls through to SMTP and logs both errors in one line. `curl_close()` removed
(no-op since PHP 8.0, deprecated in 8.5).

## 23 Oct 2026 - /brand-launch + four service pages

**The research that set the strategy.** The owner asked to match
blackboldgraphics.com. Two findings changed the plan:

1. **Standalone digitizing is a bad market to enter.** Measured from vendor
   pricing pages: $8-15 flat rate is common, $10-25 for a left chest, with
   2-12 hour turnaround advertised. Black Bold's "24-48 hours" is slow by that
   standard. Competing there means fighting $1-per-file shops for pennies.
2. **Nobody bundles the whole thing.** A search for a provider covering logo
   design + digitizing + patches + manufacturing returned none. Printful is
   closest and has no manufacturing and no logo design; patch shops give free
   digitizing only with patch orders. A founder with a name currently hires
   four suppliers.

So digitizing is positioned as the **on-ramp to manufacturing**, not a product
to win on price. The defensible claim: every other digitizer emails a file and
never learns what happened to it; we sew the garment, so density is set for
the actual fabric.

**Owner decisions, 23 Oct 2026** (recorded because the pages depend on them):
- Original logo design from just a brand name: **yes, in-house**
- Pricing: **included with a production order, quoted standalone**
- Patch types: **embroidered, woven, chenille, PVC/rubber and leather** - all four

**Built:** `/brand-launch` (hub, 6-step HowTo) plus `/embroidery-digitizing`,
`/vector-art-conversion`, `/custom-patches`, `/sublimation-printing`. Static
pages in the existing design system - no bundle patching. Each carries one
JSON-LD @graph (Breadcrumb + WebPage + Service + FAQPage; the hub uses HowTo)
and an inline enquiry form posting to the existing endpoint.

**No price is printed anywhere.** The owner approved the pricing MODEL, not
figures. Pages state "included with a production order, quoted separately if
you want the files alone" and nothing more.

**Imagery: Vertex AI, and only abstract macros.** Google Cloud access was
already present (account powerwealthenterprise@gmail.com, project
storehouse360, billing + aiplatform enabled - no auth command needed).
`gemini-3.1-flash-image` returns ~1408x768 PNG. Five images generated into
`dist/images/services/`, 0.8 MB total: thread, fabric, dye, film and a
workbench flat lay. **Nothing resembling a finished garment, a mockup or a
client product** - after the KWG notice, a generated image that reads as real
work is the one thing this site must not publish.

Gotcha: `gcloud` on Windows is a `.cmd` shim, so Python's `subprocess` cannot
resolve it (`WinError 2`). Pass the token in from the shell:
`export GCP_TOKEN=$(gcloud auth print-access-token)`.

Honesty content worth keeping: the sublimation page states plainly that it
cannot work on cotton and cannot print white, and the digitizing page lists
what fails in thread (text under ~5 mm, gradients, thin strokes). Telling a
buyer what will not work is the cheapest trust you can buy, and it matches the
warning already built into the /design configurator.
